## 4. Bug and Blind Spot List

Since virtually nothing is implemented, these are pre-implementation bugs and design risks that must be addressed proactively:

| ID | Type | Description | PRD Ref | Risk |
|---|---|---|---|---|
| BUG-001 | Namespace collision | Project assembly name uses underscored namespace (`Prior_Authorization_Workflow_Tracker`) but directory and solution use spaces. This can cause subtle reference issues in test projects. | — | Low |
| BUG-002 | Concurrency — rowversion | `PaRequests.RowVersion` (rowversion / timestamp) requires special EF Core configuration (`IsRowVersion()`). Missing this causes silent last-write-wins instead of the required `DbUpdateConcurrencyException`. | §7.1 | High |
| BUG-003 | Soft delete not applied globally | `IsDeleted` on `PaRequests` must be applied as a global query filter in `AppDbContext`. Without `HasQueryFilter(r => !r.IsDeleted)`, deleted records will leak into all queries silently. | §9 BR-014 | High |
| BUG-004 | SYSTEM user reserved identity | `ExpirationJob` uses a reserved `SYSTEM` user for audit entries. If the seeder runs before confirming this user exists, the hosted service will throw FK violations on the `ChangedByUserID` column at runtime. | §8.6 | Medium |
| BUG-005 | BR-005 duplicate check scope | The duplicate active-request check (BR-005) must match on `InsurancePlanID` (not payer name). Querying `InsurancePlans.PayerName` instead of `InsurancePlanID` would allow the rule to be bypassed when a patient holds two plans from the same payer. | §9 BR-005 | High |
| BUG-006 | Appeal deadline off-by-one | BR-008 appeal window is `DecisionRenderedAt + AppealDeadlineDays`. Using `<` vs `<=` on the deadline date boundary will either allow or block appeals filed exactly on the deadline day. Must be explicitly specified (< vs <=) and tested. | §9 BR-008 | Medium |
| BUG-007 | `AuthorizationStartDate` past-date check | BR-011 says start date must be ≥ the current date **at time of approval**. Using `DateTime.Now` directly in the service makes this non-deterministic in tests. Requires `IDateTimeProvider` injection. | §9 BR-011 | Medium |
| BUG-008 | ExpirationJob timer drift | `IHostedService` periodic timer using `Task.Delay` can drift across DST transitions, causing double-fires or missed fires. PRD acknowledges this as a known limitation but the implementation must still guard against double-expiration of the same request. | §8.6 | Low |
| BUG-009 | Provider comment visibility | `PaComments.IsInternalOnly` must be enforced in the query layer, not just the UI. If `GetComments()` returns all records and the component filters them, a role-switching attack (or a direct API call, if any) bypasses the filter. | §8.3 | Medium |
| BUG-010 | CSV export — encoding | CsvHelper default UTF-8 BOM handling must be configured explicitly to ensure Excel compatibility. Missing BOM causes garbled characters for non-ASCII patient names in Excel on Windows. | §8.10 | Low |
| BUG-011 | `RequestNumber` collision under concurrent inserts | Auto-generated `PA-YYYY-NNNNN` using MAX(ID)+1 or sequence is vulnerable to race conditions under concurrent submissions. Should use a database sequence or `IDENTITY`-based approach. | §8.1 | Medium |
| BUG-012 | `IsActive` on `Users` not enforced | PRD says `IsActive` extends `AspNetUsers`. If a deactivated user's session stays active in a Blazor Server circuit, they can still act. `ICurrentUserService` must check `IsActive` on each circuit operation, not just login. | §4.5, §10 | High |
| BUG-013 | Withdrawn status from Draft | FR-004 states "Draft requests should be deleted, not withdrawn." The state machine must explicitly **reject** a `Draft → Withdrawn` transition and instead route through the hard-delete path (BR-014). | §8.4, §9 BR-009 | Medium |
| BUG-014 | BR-013 re-submission check timestamp | Checking "new comment or document after PendingInfo entry" requires knowing **when** the request entered `PendingInfo`. This must be read from `PaStatusHistory` (the last `ToStatus = PendingInfo` row), not from `UpdatedAt`, which is overwritten. | §9 BR-013 | Medium |
| BLIND-001 | No audit on login/failed login | §11 requires `User.Login` and `User.FailedLogin` audit events. These require hooking into ASP.NET Core Identity's `SignInManager` events, which is non-trivial and often forgotten. | §11 | Medium |
| BLIND-002 | No `CorrelationId` linkage | `AuditLogs.CorrelationId` must be populated from Serilog's `{CorrelationId}` enricher or a middleware-injected header. Without plumbing this through `IAuditService`, the column will always be null. | §7.1 | Low |
| BLIND-003 | `IpAddress` in audit log | `AuditLogs.IpAddress` requires `IHttpContextAccessor`. In Blazor Server, `HttpContext` is only available during the initial request, not in subsequent SignalR messages. Must capture and cache IP at connection time. | §7.1, §11 | Medium |
| BLIND-004 | No reconnect overlay customization | NFR-011 requires a visible "reconnecting" indicator. Blazor's default overlay is minimal; the PRD requires a user-visible message. Needs CSS or component override. | §15 NFR-011 | Low |
| BLIND-005 | No `AsNoTracking()` enforcement | NFR-002 requires all read-only queries use `AsNoTracking()`. Without a code-review checklist or a wrapper pattern, individual developers will forget this on ad-hoc queries. | §15 NFR-002 | Low |

## 6. Phased Roadmap Overview

```
Phase 1 — Foundation          (sequential; ~1–2 days)
  NuGet packages → Models → DbContext → Migrations → Program.cs wiring

Phase 2 — Core Infrastructure (some parallel; ~1–2 days)
  Exception hierarchy │ Abstractions (ICurrentUserService, IDateTimeProvider)
  AuditService        │ Serilog config
  Seed data           │ Error middleware

Phase 3 — Service Layer       (two parallel tracks; ~3–4 days)
  Track A: WorkflowService → PaRequestService → BusinessRuleValidator
  Track B: NotificationService → ExpirationJob → ReportingService → UserManagementService → CsvExportService

Phase 4 — UI Components       (sequential per dependency; ~4–5 days)
  Identity/Auth → NavMenu → Layout primitives →
  Dashboard → Queue → Submit → Detail → Edit → Reports → Admin → Notifications

Phase 5 — Unit Tests          (parallel with Phase 3 & 4 per service; ~2–3 days)
  Tests.Unit project → WorkflowService tests → BusinessRuleValidator tests →
  PaRequestService tests → AuditService tests → ReportingService tests

Phase 6 — NFR Polish          (~1 day)
  AsNoTracking audit → SignalR reconnect → Anti-forgery audit → Error correlation IDs
```

Total estimated effort: **12–17 developer-days** (single developer, uninterrupted).

## 8. Parallel Worktree Plan

Git worktrees allow multiple branches to be checked out simultaneously in separate directories, enabling true parallel development without stashing or switching.

### Recommended Worktree Layout

```
d:\Dev\Prior_Authorization_Workflow_Tracker\           ← main branch (integration)
d:\Dev\Prior_Authorization_Workflow_Tracker-foundation\ ← worktree: feature/foundation
d:\Dev\Prior_Authorization_Workflow_Tracker-services\   ← worktree: feature/service-layer
d:\Dev\Prior_Authorization_Workflow_Tracker-ui\         ← worktree: feature/ui-components
d:\Dev\Prior_Authorization_Workflow_Tracker-tests\      ← worktree: feature/unit-tests
```

Setup commands:
```bash
git worktree add ..\Prior_Authorization_Workflow_Tracker-foundation feature/foundation
git worktree add ..\Prior_Authorization_Workflow_Tracker-services feature/service-layer
git worktree add ..\Prior_Authorization_Workflow_Tracker-ui feature/ui-components
git worktree add ..\Prior_Authorization_Workflow_Tracker-tests feature/unit-tests
```

### Worktree Assignments

#### Worktree 1 — `feature/foundation` (solo, sequential)
**Tasks:** T01 → T02 → T03 → T04 → T05 → T09 → T11  
**Rationale:** All foundational tasks are sequential and establish the schema that every other worktree depends on. This worktree must be merged to `main` first.  
**Gate before merge:** `dotnet ef database update` runs clean; seed data verified; app serves login page.

#### Worktree 2 — `feature/core-infra` (starts after T05 merged)
**Tasks:** T06, T07, T08, T10 (all parallel within worktree)  
**Rationale:** Exception hierarchy, abstractions, AuditService, and middleware are independent of each other but all require the NuGet packages from T01. Can all be coded in parallel by splitting files across developers or coding them sequentially in one sprint.  
**Gate before merge:** All T06–T10 classes compile and have stub unit tests passing.

#### Worktree 3 — `feature/service-layer-workflow` (starts after T06/T07/T08 merged)
**Tasks:** T12 → T13 → T14 (Track A)  
**Rationale:** WorkflowService, PaRequestService, and BusinessRuleValidator have internal dependencies (T12 needs T06/T07; T14 uses FluentValidation independently). T13 uses T12 for status transitions.  
**Note:** T14 can be started in parallel with T12 since it has no dependency on WorkflowService.

#### Worktree 4 — `feature/service-layer-support` (starts after T07/T08 merged)
**Tasks:** T15, T16, T17, T18, T19 (Track B)  
**Rationale:** Notification, UserManagement, and Expiration services are independent of Track A except T16 (ExpirationJob) which depends on T12 and T15. Start T15/T17/T18 immediately; T16 waits for T12 merge; T19 waits for T17.

#### Worktree 5 — `feature/ui-components` (starts after T05 merged; most pages wait for Phase 3)
**Tasks:** T20 → T21 → T22 (early); then T23–T30 (after Phase 3 services merged)  
**Rationale:** T20–T22 (Identity UI, NavMenu, shared primitives) only depend on the scaffold and Identity setup, so they can begin as soon as T05 is complete. The application pages (T23–T30) must wait for their backing services.

#### Worktree 6 — `feature/unit-tests` (T31 starts after T01; service tests follow each service)
**Tasks:** T31 (infrastructure) → T32–T36 (one per service)  
**Rationale:** Test project setup (T31) only needs NuGet packages. Individual service test files can be written as each service completes — T32 can be written in parallel with T12 if the service interface is defined first.

### Merge Sequence

```
feature/foundation          ─► main  (gate: app starts, DB migrates)
feature/core-infra          ─► main  (gate: compiles; audit service tested)
feature/service-layer-*     ─► main  (gate: unit tests pass)
feature/ui-components       ─► main  (gate: manual smoke test all pages)
feature/unit-tests          ─► main  (gate: dotnet test --coverage meets targets)
```

## 9. Recommended First 3–5 Tasks

These are the highest-priority tasks to start immediately, in order:

### Task 1 — T01: Add NuGet packages
**Why first:** Every subsequent task depends on having packages available. This is a 5-minute change to the `.csproj` with zero risk of conflict.  
**Files:** `Prior Authorization Workflow Tracker.csproj`  
**Action:** Add EF Core, Identity EF Core, Serilog, FluentValidation, CsvHelper packages.

### Task 2 — T02 + T03: Create entity models and `AppDbContext` (can overlap with T02)
**Why second:** Models and DbContext define the shape of the entire application. Getting these right (correct FK relationships, concurrency token for `RowVersion`, global soft-delete filter, index definitions) prevents cascading schema fixes later.  
**Key risk to get right now:** `BUG-003` (global query filter for `IsDeleted`), `BUG-002` (RowVersion as concurrency token), `BUG-005` (InsurancePlanID FK vs PayerName in BR-005).  
**Files:** `Models/` (10 entity files), `Data/AppDbContext.cs`

### Task 3 — T05: Wire `Program.cs`
**Why third:** Identity middleware must be inserted in the correct pipeline order (before `UseAuthorization`, after `UseAuthentication`). Getting this wiring wrong causes subtle runtime failures. Do this once and do it correctly before any UI work starts.  
**Files:** `Program.cs`, `appsettings.Development.json` (add connection string)

### Task 4 — T06 + T07: Exception hierarchy and service abstractions (parallel)
**Why fourth:** `ICurrentUserService` and `IDateTimeProvider` are injected into every service. Defining these interfaces before writing the services prevents costly refactors. The exception hierarchy is referenced in every `WorkflowService` method.  
**Files:** `Exceptions/` (5 files), `Services/Abstractions/` (4 files)

### Task 5 — T09: Seed data
**Why fifth:** Seed data is the foundation for all manual testing and the dashboard demos. Writing it early means every subsequent UI task can be verified against realistic data immediately rather than writing a test manually each time.  
**Key risk:** SYSTEM reserved user must be created before `ExpirationJob` is registered or it will FK-violate on first run.  
**Files:** `Data/DbSeeder.cs`; called from `Program.cs` in `IsDevelopment()` guard
